# Star Castle 2 — Project Manager Plan

## Objective
Build and publish a complete, browser-playable Star Castle 2 remake in `/Users/davidpence/star-castle-2`, using OpenCode exclusively for implementation and debugging. The target is a high-fidelity, original-authored recreation of the 1980 Cinematronics arcade experience, not a ROM/assets extraction.

## Reference facts used for the brief
- Original: 1980 Cinematronics multidirectional/vector arcade shooter.
- Black field with bright monochrome vector lines and color-overlay-style ring/castle accents.
- Player ship rotates, thrusts with inertia, and fires in the facing direction.
- Objective: destroy the central enemy cannon protected by three rotating concentric defensive rings.
- Mines emerge from the castle/core, pass through defenses, and home toward the player.
- Castle/core tracks the player; later levels increase mine speed, ring rotation, and core tracking difficulty.
- Controls are button-driven rather than joystick-driven: rotate left/right, thrust, fire; hyperspace is reference-dependent and must not be invented as required behavior unless verified.
- Presentation must include attract/title state, start, gameplay, death/reserve, level transition, score/lives, game over, and restart.
- Audio must be synthesized/original-authored, with distinct thrust, fire, mine, impact, castle-hit, core-hit, death, level-clear, and attract cues; no sampled cabinet audio.

## 20 implementation loops

### Phase A — Rules and cabinet foundation
1. Establish a deterministic rules module and verification harness; preserve the existing browser foundation only where useful.
2. Implement vector renderer: black background, glow, line persistence/flicker simulation, ring segments, cannon, ship, mines.
3. Implement attract mode, high-score panel, start flow, HUD, pause/mute, keyboard and touch control visibility rules.
4. Implement ship rotation, thrust inertia/friction, screen wrapping, fire cooldown, projectile lifetime, and hyperspace only if justified by reference research.
5. Implement three rotating shield rings with segment damage, shot passage/openings, regeneration behavior, and deterministic tuning.

### Phase B — Core gameplay
6. Implement central cannon/core tracking, firing, shield interaction, and core destruction condition.
7. Implement mine spawning from the core, homing behavior, collision/death logic, and mine speed progression.
8. Implement player projectiles, ring/cannon/mine collision priority, scoring, lives/reserves, and restart state reset.
9. Implement level progression: new gun/core, restored rings, increased difficulty, level-clear presentation, and deterministic level seed/state.
10. Implement game-over, attract return, high-score persistence, and a clean new-session boundary with no stale timers/entities.

### Phase C — Sound and fidelity polish
11. Implement Web Audio unlock, master mute, synthesized vector-arcade sound palette, envelopes, and safe audio fallback.
12. Tune movement/shooting/ring rotation/mine pursuit against reference footage and documented behavior; remove invented mechanics that reduce fidelity.
13. Tune vector colors/overlay approximation, line weights, glow, flicker, screen composition, and cabinet-like typography.
14. Add impact/explosion particles and brief screen effects that preserve the restrained vector presentation rather than modern neon clutter.
15. Add responsive portrait/landscape touch controls, safe-area layout, keyboard accessibility, and reduced-motion/audio-safe fallbacks.

### Phase D — Judge passes and release
16. Add deterministic unit/rules tests for ring damage/regeneration, mine pursuit, score, level difficulty, state transitions, and collision priority.
17. Add browser runtime probe: collect `error` and `unhandledrejection` before starting, exercise title→play→death→restart→level progression, and wait through delayed timers.
18. Add static/source audit: no conflict markers, no external runtime dependencies, no ROM/code/audio assets, no per-frame object leaks, no undefined called functions.
19. Perform a visual/interaction audit at desktop and narrow mobile sizes; fix only issues found and re-run all tests/probes.
20. Finalize README, provenance/licensing note, changelog/release marker, GitHub Pages deployment, and live-site verification with cache-buster.

## Judge rubric / acceptance gates

A loop is not accepted from OpenCode unless it provides:
1. Files changed and a concise implementation summary.
2. Tests/commands actually run with exit status and output.
3. A clear distinction between static evidence, local runtime evidence, and deployed evidence.
4. No unverified claim of arcade accuracy.

Final release gates:
- `npm test` and `npm run check` pass.
- Browser runtime probe reaches title→play, rotates/thrusts/fires, damages rings, spawns/pursues mines, handles death/restart, and advances level without runtime errors.
- Ring/cannon/core behavior is playable and deterministic enough to audit.
- Audio unlocks only after user gesture, mute works, and synthesized cues exist for the major gameplay events.
- Canvas remains responsive and playable on desktop and portrait touch layout.
- README documents controls, provenance, limitations, and how fidelity was judged.
- GitHub repository is public, main branch is pushed, Pages is enabled, and the live URL serves the verified build.
- Do not call the result “95% accurate” unless the rubric passes; report measured pass/fail evidence and remaining gaps honestly.

## Project-manager operating rule
Hermes does not author or patch project code. OpenCode is the coding/debugging worker. Hermes inspects, runs read-only verification, judges against this plan, and sends correction briefs back to OpenCode until the release gates pass.
